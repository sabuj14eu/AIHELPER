# Brother Developer repository layout

The `brother-developer` repository is small and flat. Top level: `CLAUDE.md` (constitution), `README.md` (Phase 1 scaffold notes and the pre-split CLI lines), `pyproject.toml` (only `[tool.pytest.ini_options] testpaths = ["tests"]`), `.gitignore` (`__pycache__/`, `*.pyc`, `brother_developer/evidence/`, `.venv/`), `docs/` (spec, protocol and the five reports), `brother_developer/` (the package) and `tests/`. The package `brother_developer/` holds six modules plus three data directories: `evidence/` (run manifests), `ledger/ledger.jsonl` (the hash chain) and `memory/` with `adr/` and `bugs/`. There is no `setup.py`/build metadata beyond pytest config; the package is run in place with `python3 -m brother_developer`.

# The Brother Developer CLI (`brother_developer/__main__.py`)

`brother_developer/__main__.py` is the entry point. It resolves `HERE` to the package directory and `ROOT = HERE.parents[1]` — the workspace directory that holds this repo beside the three trading repos — and opens the ledger at `HERE / "ledger" / "ledger.jsonl"`. Commands (`python3 -m brother_developer <cmd>`):
- `manifest [task words]` — builds a governance manifest over ROOT, writes it to `brother_developer/evidence/<run_id>.json`, appends a ledger row of kind `manifest` with `run_id` and `fingerprint`, prints `run_id`, `repos`, `config_fingerprint`.
- `scan` — SYSTEM MAP per repo (file counts, by-risk histogram, network files), entries omitted from stdout.
- `test <repo>` — runs that repo's pytest through the test engine, appends a ledger row of kind `test` with the verdict.
- `ledger verify` — prints the chain verification result.
- `memory list` — prints bug ids with the first 60 characters of their problem, and ADR stems.
The ROOT expression was a P3 bug (it once read `HERE.parents[1].parent`, resolving to `/home`, so the committed manifest shows every repo as `NOT_A_CHECKOUT`); it was fixed in Window 2 and pinned by `tests/test_brother_developer.py::test_the_cli_resolves_the_workspace_one_level_up`.

# The Brother Developer manifest (`brother_developer/manifest.py`, spec §2.2)

The Brother Developer manifest answers "what exactly was investigated, on what code, with what tools — reproducible later". `manifest.build(root, task, tools, files, tests, diff_text, sources, agent)` returns a dict with: `run_id` (`BD-<UTC yyyymmdd-HHMMSS>-<6 hex>`), `ts`, `task`, `repos` (per repo: `path`, `state` OK or NOT_A_CHECKOUT, `commit`, `branch`, `dirty`, `dirty_files`), `tools`, `files`, `tests`, `python`, `platform`, `packages` (versions of fastapi, sqlalchemy, pytest, jinja2, pydantic, httpx when installed), `patch_hash` (sha256 of the diff text, or null), `research_sources`, `agent` (default "unstated"), and `config_fingerprint` (first 16 hex of sha256 over repos + python + packages). `REPOS = ("Sniper-System", "brother-brain-v2", "brother_sniper_v7")`. Git failures are reported as `UNKNOWN (<exception>)` rather than raised. The only committed manifest is `brother_developer/evidence/BD-20260904-212928-9191f2.json` (task: "Job 3 rebuild + P0 memory + box flags + patch proposal"); Window 2's manifest `BD-20260904-224305-190e6f` is named in `docs/WINDOW2_ISO02_ISO09_2026-09-05.md` but not committed (the directory is gitignored).

# The Brother Developer ledger (`brother_developer/ledger.py`, spec §2.3)

The Brother Developer ledger is an append-only JSONL file, `brother_developer/ledger/ledger.jsonl`, in which each row hashes the previous one. `Ledger.append(kind, payload)` builds `event = {seq, kind, ts (UTC ISO), payload}`, takes `prev` = the last row's `hash` (or `GENESIS`, 64 zeros, for row 1), computes `hash = sha256(prev + json.dumps(event, sort_keys=True))`, and writes `{**event, prev, hash}` as one line with sorted keys. `Ledger.verify()` walks the file from GENESIS and returns `{"ok": True, "rows": n, "head": hash}` or `{"ok": False, "broken_at": seq, "rows": n}` at the first row whose `prev` or recomputed hash does not match. `tests/test_brother_developer.py::test_ledger_is_hash_chained_and_tamper_evident` edits row 1's payload and asserts `broken_at == 1`.

The committed ledger holds 39 rows (2026-09-04T21:29Z to 2026-09-05T12:46Z). Row kinds observed, in order of first appearance: `manifest`, `audit_missing`, `test`, `memory`, `patch_proposed`, `session_end`, `box_witness`, `patch_scripted`, `box_deploy_step`, `box_verify`, `patch_applied_repo`, `iso01_resolved`, `platform_reply`, `proposal`, `work_order`, `fix`, `window2_verified`, `finding_closed`, `converged`, `job3_closure`, `job9`, `job8`, `p0_fixed_repo` (rows 29–38, one per P0), `p0_queue_complete` (row 39). When two windows merged their branches the chain was kept from `main` and the diverging rows re-appended (commits `1e9e1d1`, `a7cc1a1`; row 23 carries the note "re-appended after merging main (chain kept from main)"). The ledger stores no secret values: box witnesses record `ADMIN_HALT_TOKEN` as "set" and NSSM env values as key names only.

# Brother Developer memory records (`brother_developer/memory.py`, spec §20/§21)

Brother Developer memory is "structured engineering memory: bugs, fixes, ADRs as JSON/Markdown records with a fixed schema — never vague AI memory". A bug record must carry all of `REQUIRED = (id, date, repo, commit, problem, root_cause, solution, tests, risk, status, files, do_not_reintroduce)`, with `risk` in P0–P4 and `status` in `open | resolved | watch | rejected`; `Memory.add_bug` raises `ValueError` listing every missing or invalid field, and `test_memory_records_are_structured_and_seeded` validates every committed record. `Memory.touching(path_fragment)` returns the records whose `files` mention a path — "what memory says before you touch this file" (spec §3.1). Records live in `brother_developer/memory/bugs/<id>.json`; ids follow `BUG-<date>-<slug>`, and the ISO records `BUG-2026-09-04-ISO01-…` … `BUG-2026-09-05-ISO24-…`. Fourteen records are committed: three seeded platform bugs (scalar offset P2, trade twins P0, RETEST persistence P1) and eleven ISO P0s. The `commit` field of a record is the commit at which the bug was observed (e.g. v7 `c1618f5`, brain `cfc52e9`), not the fix commit; the fix commit is written into `solution`.

ADRs live in `brother_developer/memory/adr/ADR-001.md` … `ADR-010.md`, each seven lines (title, Status, Decision, Consequence). `Memory.adrs()` lists their stems and the test pins exactly ten.

# The Brother Developer SYSTEM MAP (`brother_developer/repo_map.py`, spec §6, §7, §36)

`repo_map.scan_file(path)` parses a Python file with `ast` and returns its functions, classes, top-level import roots, whether it touches the network (imports any of httpx, requests, aiohttp, MetaTrader5, socket), whether it touches a database (sqlalchemy, psycopg, sqlite3), and its risk class; unparsable files are `NOT_PARSED`. `scan_repo(root, limit=4000)` walks `*.py` (skipping `.venv` and `node_modules`) and returns counts by risk class and the list of network files. `callers_of(root, name)` is the dependency-awareness helper: every file whose text names the symbol. `risk_class` is keyword-based and documented as a floor for review, never a verdict.

# The Brother Developer test engine (`brother_developer/test_engine.py`, spec §2.1)

`test_engine.run(repo, python, args=("-q", "-p", "no:cacheprovider"), timeout=1200)` runs `python -m pytest` in the repo, returns NOT TESTED when there is no `tests/` directory, UNKNOWN on timeout, NOT RUNNABLE when the interpreter is missing, and otherwise `classify(returncode, output)` plus the command and the last 1500 characters of output. `classify` never turns an unparseable or empty result into PASS (developer__laws.md has the branch table).

# The Brother Developer replay contract (`brother_developer/replay.py`, spec §24)

`replay.compare(old, new, fields=FIELDS)` is the only replay code in Phase 1: the runners that push the same inputs through OLD and NEW code are Phase 3. It compares twelve execution-relevant fields and answers UNKNOWN / UNCHANGED / CHANGED; the CHANGED result carries the BEHAVIOR CHANGED note and explicitly refuses to say IMPROVEMENT or REGRESSION. In the P0 queue the actual replays were written as pytest fixtures inside the trading repos (e.g. `test_replay_ISO19_twelve_real_rows_behavior_changed_report` in `brain/tests/audit/2026-09-05_iso19/`), not through this module.

# Diagnosis and proposal formats

Two fixed formats appear in the Brother Developer reports. The diagnosis format (`CLAUDE.md` rule 2) is SYMPTOM · ROOT CAUSE · AFFECTED · WHY TESTS MISSED IT · FIX · RISKS · TEST PLAN; in the memory schema this maps to `problem`, `root_cause`, `files`, `tests`, `solution`, `risk`, `do_not_reintroduce`. The patch-proposal format (spec Phase 2, `docs/BROTHER_DEVELOPER.md` §3) is the six-part diff explanation BEFORE / WHY WRONG / AFTER / WHY CORRECT / WHAT COULD BREAK / HOW TESTED; `docs/JOB3_ISOLATION_2026-09-04.md` §4 (ISO-01) and `docs/JOB8_9_TRADING_LOGIC_2026-09-05.md` §3–§4 (ISO-19, ISO-24) are complete instances, each ending "NOT applied". A P0 proposal's HOW TESTED enumerates unit, failure injection, regression, replay, and names the box step and human approval as the release gate.

# Golden fixtures and evidence tests

Evidence tests live under `tests/audit/<date>_<job>/` in the repo they test and are marked `# EVIDENCE — reproduces finding X, keep` (`docs/SESSION_PROTOCOL.md` step 5). Naming convention from the reports: `test_repro_<ISO>_*` PASSES while the finding is reproducible (green means the gap is still there); `test_holds_*` is an invariant that holds today; `test_golden_<ISO>_*` is the inverted reproduction after a fix (the correct behaviour). To keep a reproduction re-runnable after the fix, the pre-fix file is copied into `fixtures/` — `brother_sniper_v7/tests/audit/2026-09-04_job3/fixtures/sniper_executor_prepatch_c1618f5.py` and `brother-brain-v2/tests/audit/2026-09-04_job3/fixtures/mt5_bridge_prepatch.py` — and the repro test loads that copy by path. The fixtures use a `FakeMT5` terminal module that records every `order_send` with the account it hit (and, after commit `eef7c1b`, `shutdown()` and `honour_login`), a throw-away Ed25519 key, Flask test clients for the v7 bridge and FastAPI/httpx for the v18 route tests; no broker, no network, no live checkout.

This repo's own evidence suite is `tests/audit/2026-09-04_job3/test_cross_arm_isolation.py` (seven tests) for properties that need both arms at once: ISO-16 repro and golden (v18 halt engages the shared witness and the v7 bridge refuses; v7 `/admin/halt` is read by v18), ISO-16b static check that both trees name the same `GLOBAL_STOP_FILE` default paths (`C:\brotherbot\GLOBAL_STOP` and `/var/lib/brotherbot/GLOBAL_STOP`), ISO-01/ISO-09 cross-arm repro and both golden inversions, and ISO-08/ISO-13 (dedupe keys omit the account, still FAIL). It loads `brother_sniper_v7/tests/audit/2026-09-04_job3/conftest.py` by path for `FakeMT5` and `load_v7_bridge`, needs flask and loguru, and skips as NOT RUNNABLE otherwise.

# The ten bot-session jobs (spec §45)

`docs/BROTHER_DEVELOPER.md` §5 defines Jobs 1–10, every one READ + TEST + REPORT first with a patch as a separate gated step: Job 1 dual-MT5 account isolation audit (trace `account_id`, deliverable table); Job 2 trace the whole path with one correlation set per hop (`trace_id, signal_id, decision_id, account_id, executor_id, broker_ticket, position_ticket`); Job 3 the ten isolation tests; Job 4 pending-order lifecycle (no LIMIT→MARKET, ADR-006); Job 5 emergency-stop propagation; Job 6 daily-loss isolation (`EquityGuard` per account); Job 7 duplicate prevention on `(account_id, signal_id)`; Job 8 fallback audit (`or 0`, `default=`, `except: pass`, `fallback`); Job 9 LLM-computed execution values (ADR-005); Job 10 golden fixtures from the memory records. Done so far: Job 3 (closed 2026-09-05), Jobs 8 and 9 (2026-09-05), ISO-14 as a Job 4 finding met on the way; Jobs 1, 2, 5, 6, 7 and 10 exist only as far as Job 3's fixtures and the P0 fixes reached them (`docs/JOB3_ISOLATION_2026-09-04.md` §5).

# Sandbox worktree and release gate

The sandbox worktree is Phase 2's unit of work: "worktree per task, patch, targeted + regression tests, diff explanation ... Never touches a box checkout" (`docs/BROTHER_DEVELOPER.md` §3). In practice the windows worked on designated branches (`claude/sniper-isolation-audit-completion-xdj6z4`, `claude/gold-ny-breakout-correctness-ek8562`) pushed empty at session start, verified each other in "scratch worktrees" (`docs/JOB3_ISOLATION_2026-09-04.md` §10) and ran regression "in clean worktrees at the branch heads" (`docs/P0_RELEASE_REPORT_2026-09-05.md` §2). Shyam converged the branches from separate audit clones under `/home/shyam/audit-2026-09-04`, never a live checkout (§11).

The release gate is the human step that separates `PASS (repo)` from a box verdict. `docs/P0_RELEASE_REPORT_2026-09-05.md` §9 defines what a deploy needs: coupled deploys (brain + v18 executor together for ISO-10; v7 bridge + v7 bot together for ISO-03), the env keys each service needs (`EXECUTOR_IC_MARKETS_ACCOUNT`, `MT5_LOGIN`/PASSWORD/SERVER, `V7_MT5_LOGIN`, `V7_MAGIC_NUMBER`, `ADMIN_HALT_TOKEN`, a shared writable `GLOBAL_STOP_FILE` path), the witness to read after each deploy (`/health` fields `account_login`, `trade_mode_name`, `global_stop`, `account`, `magic`, `balance_state`), and the ceremony backup → compile → restart → verify in logs/journal.
