# Accounting application architecture (components with file paths)

## Big picture

The accounting app at `account.signalmesh.dev` is the Liberu accounting ERP (installed and pinned, providing ledger, invoicing, banking, reporting) with `modules/poland` mounted as a Composer path repository. The Poland module is layered one way only: `Laravel layer → Reporting → Calculators → Rates → Domain`. `Domain`, `Rates`, `Calculators` and `Reporting` contain no Laravel, which is why `modules/poland/bin/pl-tax` works with nothing but PHP; `bin/check-isolation.sh` check 4 fails the build if `Illuminate\` appears in those directories. The app has its own DB, queue, storage and login. Source: `docs/ARCHITECTURE.md`.

## Domain layer — modules/poland/src/Domain

**`Poland\Domain\Money`** (`src/Domain/Money.php`): an exact PLN amount held as an integer number of grosze (`public readonly int $grosze`); no float survives into a stored value. Constructors: `Money::grosze(int)`, `Money::zero()`, `Money::parse(string|int|float)` — a strict parser accepting "48 500,00", "48500.00", "48,500.00"; it treats a 3-digit group after a comma as thousands and rejects anything it cannot read one way (the doc comment notes ambiguous separators are the most common way a cash-register total is entered wrong by a factor of 100). Arithmetic: `plus`, `minus`, `times(float)` (rounds half-up to whole grosze), `dividedBy`, `roundedToZloty()` (Ordynacja podatkowa art. 63 § 1), `clampAtZero`, `max`, `min`, `sum(iterable)`. `toFloat()` is display only. `format()` renders "1 234,56 zł" with a non-breaking thousands space; `jsonSerialize()` renders "1234.56".

**`Poland\Domain\Period`** (`src/Domain/Period.php`): a settlement month (year 2000–2100, month 1–12). `Period::of(y,m)`, `Period::parse("2026-08")`, `firstDay()`, `lastDay()`, `next()`, `previous()`, `yearToDate()` (January through this month), `quarter()`, `isQuarterEnd()`, `monthsSince()`, `sortKey()`, `label()` (Polish month names), `toString()` "YYYY-MM".

**`Poland\Domain\TaxProfile`** (`src/Domain/TaxProfile.php`): everything about a taxpayer that changes the arithmetic, with no defaults for the decisions only the taxpayer can make. Fields: `name`, `pitRegime` (`PitRegime`), `vatStatus` (`VatStatus`), `zusScheme` (`ZusScheme`), `businessStartedAt` (`Period`), `businessStartedOnDay` (1–31), `nip` (validated by checksum, weights 6,5,7,2,3,4,5,6,7 mod 11), `lumpSumRate` (required for LumpSum; validation range >0 and ≤0.20), `vatSettlement` (`VatSettlementFrequency`), `sicknessInsurance` (voluntary, default true), `malyZusPlusBase` (required for MalyZusPlus), `accidentRate` (override for 10+ insured; null uses 1.67%), `deductionBasis` (`ContributionDeductionBasis`, default AccruedForMonth), `healthBandFromPreviousYear` + `previousYearRevenue`, `reduceHealthBandBySocial` (default true, art. 81 ust. 2g election), `cashRegisterLetters`. Methods: `monthsInBusinessAt()`, `zusSchemeExpiredAt()` (reported, never auto-corrected), `isValidNip()`.

**Enums** (`src/Domain/Enums/`): `PitRegime` {Scale 12%/32%, Flat 19%, LumpSum ryczałt; `deductsCosts()` false only for LumpSum; `healthDeduction()` None / CappedAnnualLimit / HalfOfPaid}; `VatStatus` {Registered, ExemptBySize (art. 113), ExemptByActivity (art. 43); `settlesVat()`, `isLimitDependent()`}; `ZusScheme` {UlgaNaStart (6 months, health only), Preferential (24 months, 30% of minimum wage), MalyZusPlus (base supplied, 36-in-60 limit configured not derived), Full (60% of forecast average wage)}; `ContributionDeductionBasis` {AccruedForMonth (memoriałowo), PaidInMonth (kasowo)}; `HealthDeduction`; `VatSettlementFrequency` {Monthly → JPK_V7M, Quarterly → JPK_V7K}.

Other domain objects: `FiscalSalesReport` (gross per VAT designation, `revenueForIncomeTax($vatStatus)`, `turnoverForExemptionLimit()`, optional per-line ryczałt rate), `SalesLine`, `PurchaseRegister` (`deductibleCostsNet`, input VAT), `Ledger` (`salesFor`, `purchasesFor`, `missingMonths`, `hasAnyPurchases`).

## Rates layer — modules/poland/src/Rates and config/rates

`RateRepository::default()` loads `config/rates/*.php` (path overridable via `POLAND_RATES_PATH` / `poland.rates_path`); `RateTable`, `RateVersion`, `RateProvenance`, `VerificationStatus` {Official, Secondary, Unverified}, `MissingRateException::for($tables, $period)`, `UnverifiedRateException::for($period, $unverified)`. Overlapping versions are rejected at construction; an open-ended version may not be followed by another; a version without a version identifier or without complete provenance fails to load; `status => 'official'` requires a non-empty `source_url`. `RateRepository::coverage($period)` returns `['ok' => bool, 'missing' => [...]]`; CI's `rate-coverage` job checks six months ahead. Source: `docs/ARCHITECTURE.md`, `RateTableTest` names.

Each version carries: `version`, `effective_from`, `effective_to`, the values, `meanings` (Polish meaning of each value), and `provenance` {`status`, `source_document`, `source_url`, `official_source_url`, `published_on`, `checked_on`, `checked_by`, `notes`}.

## Calculators — modules/poland/src/Calculators

`ZusCalculator` (`calculate($profile, $month, $previousMonthIncome, $revenueYtd, $socialPaidSoFar)` → `ZusSettlement` with `socialTotal`, health, `total`, notes), `VatCalculator` (→ `VatSettlement` with output VAT extracted gross×rate/(1+rate), input VAT, `amountToPay`, surplus carry-forward, `settlesVat`, exemption-limit warnings), `PitCalculator` with `PitInput` (revenueYtd, costsYtd, socialDeductible, healthPaid, advancesYtd, lump-sum streams, hasAnyPurchases) → `PitSettlement` (`advanceDue`, `isEstimate`, notes). Calculators branch on rate-version contents, never on hard-coded constants. Source: `SettlementEngine.php`, `docs/ARCHITECTURE.md`.

## SettlementEngine and replayYear — modules/poland/src/Reporting/SettlementEngine.php

`SettlementEngine::__construct(RateRepository $rates, bool $requireOfficialRates = false)`; `withDefaultRates()`. `settle(TaxProfile, Ledger, Period): MonthlyTaxReport` does, in order: check rate coverage (throw `MissingRateException`); compute unverified tables and throw `UnverifiedRateException` if `requireOfficialRates`; refuse a month with no sales ("an unrecorded month is not a month of zero sales"); warn about missing earlier months; run `replayYear`; compute VAT for the month; sum `totalDue = zus.total + vat.amountToPay + pit.advanceDue`; compute deadlines for zus, pit_advance and (if VAT-registered) vat, warning when the holiday calendar is unverified; add the note naming the deduction basis; warn "STAWKI NIEZWERYFIKOWANE URZĘDOWO" when rates are secondary; warn when an income regime has no costs; set `isEstimate = pit.isEstimate || (settlesVat && no purchases)`; return the report with `rateSources`, `rateProvenance`, and `ratesFitForFiling = (unverified === [])`.

`replayYear(TaxProfile, Ledger, Period $through)` walks `$through->yearToDate()` (January forward), accumulating revenue YTD, costs YTD, exemption-limit turnover YTD and advances YTD, computing ZUS for each month with the previous month's income and social paid so far (needed because the ryczałt health band may be read net of them), then PIT with cumulative inputs. It returns per-month `revenue`, `costs`, `income`, `zus`, `pit`, `turnover_ytd`. Rationale in `docs/ARCHITECTURE.md`: settling a month in isolation would drift, and the drift would be invisible.

## MonthlyTaxReport and DISCLAIMER — modules/poland/src/Reporting/MonthlyTaxReport.php

`MonthlyTaxReport` is "the whole answer in one object" and is a CALCULATION, never a filed return. `public const DISCLAIMER = 'To jest WYLICZENIE, nie deklaracja. Żadna z tych kwot nie została wysłana do ZUS ani do urzędu skarbowego. Rozliczenie z księgowym pozostaje wymagane.'` Fields: profile, period, grossSales, revenueForIncomeTax, zus, vat, pit, totalDue, deadlines (each with date, statutory, shifted, verified, label), notes, warnings, `isEstimate`, `rateSources`, `rateProvenance`, `ratesFitForFiling`. `fitForFiling()` = `!isEstimate && ratesFitForFiling`; `blockersToFiling()` lists why not. `TextReportRenderer` prints the DISCLAIMER in a "WAŻNE" box. Related: `AccountantReport`/`AccountantReportBuilder` (eight sections: summary, ZUS, PIT, VAT, financial result, payment checklist, provenance, warnings per `docs/CHANGELOG.md`), `PaymentObligation` with `PaymentStatus` {Unpaid, Paid, NothingToPay} and `ObligationKind` {Zus, Pit, Vat}, `FinancialResult`, `SettlementStage` {Calculated, Prepared, Filed; `canAdvanceTo` one step at a time}, `FilingChannel` {JpkV7, Ksef, Zus, PitReturn, Manual; `automated()` always false}.

## Ports and refusing adapters — modules/poland/src/Contracts and src/Adapters/Null

Ports: `DocumentPreparer`, `DocumentSubmitter`, `ExchangeRateProvider` (+ `ExchangeRateQuote`), `SchemaRegistry` (+ `SchemaVersion`), `FilingResult` (`accepted()` requires a non-empty reference and no error), `PreparedDocument`. Default bindings refuse: `UnconfiguredSubmitter` throws, `UnavailableExchangeRateProvider` throws, `SchemaRegistry` is empty and refuses unregistered periods. Three stages with three truth conditions: CALCULATION sets `computed_at`; PREPARATION sets `prepared_at` and a `pl_prepared_documents` row (refused when the settlement is an estimate or rates are unverified); FILING sets `filed_at` + `filing_reference` only on `FilingResult::accepted()`. `SettlementModel::stage()` derives the stage from `filed_at`/`prepared_at` rather than trusting a column. Source: `docs/ARCHITECTURE.md`.

## Standalone CLI — modules/poland/bin/pl-tax

Usage: `pl-tax --profile=firma.json --sales=2026-08:48500 [--period=YYYY-MM] [--rate=0.23] [--costs=M:NETTO:VAT] [--json] [--brief] [--year]` or `--sales-file=sprzedaz.json`. ## Deployment units and backup — deploy/, bin/

- `deploy/nginx/account.signalmesh.dev.conf`: HTTP→HTTPS redirect; root `/srv/accounting/foundation/public`; `client_max_body_size 32M`; security headers; `fastcgi_pass unix:/run/php/php8.5-fpm-accounting.sock` (its own pool); logs `/var/log/nginx/accounting.*.log`.
- `deploy/systemd/accounting-queue.service`: user `accounting`, `php artisan queue:work --queue=default --sleep=3 --tries=3 --max-time=3600`, `Restart=always`, hardened (`NoNewPrivileges`, `ProtectSystem=full`, `ReadWritePaths=/srv/accounting/foundation/storage`). `accounting-scheduler.service` (oneshot `schedule:run`) + `accounting-scheduler.timer` (every minute).
- `deploy/backup.sh`: `mysqldump --single-transaction --routines --triggers --events` to `/var/backups/accounting/db-<stamp>.sql.gz`, restores into `<db>_restore_check`, compares row counts on `pl_tax_profiles`, `pl_sales_reports`, `pl_settlements`, `pl_audit_events`, exits non-zero on mismatch, archives `storage/app`, keeps 30 days.
- `bin/data-safety-drill.sh`: dump, restore into `<db>_drill`, compare 17 tables' row counts, report checksums and bodies, audit-event count, duplicate-month and duplicate-version indexes, KSeF XML SHA-256, reconciliation decisions, settlement amounts, orphaned payment obligations; fails loudly if the drill grant is missing.
- `bin/deploy-contabo.sh`: 12-step idempotent install on Ubuntu 22.04/24.04 or Debian 12 — PHP 8.5, MariaDB, Redis, nginx, user `accounting`, root `/srv/accounting`, DB `accounting` with `GRANT ... ON accounting.*` and `accounting_drill.*`, Redis DB 3/4, writes `.env` with `POLAND_REQUIRE_OFFICIAL_RATES=true`, `KSEF_TRANSPORT_ENABLED=false`, `KSEF_TRANSPORT=disabled`, own PHP-FPM pool, vhost, certbot, systemd units, admin account; prints the URL (`/poland` is the "co muszę zapłacić" dashboard).

## Shop Profit Intelligence architecture — shop-intelligence/

Framework-free analysis core in `src/`, namespace `Shop\`, no Composer install, no database, no Laravel; `php bin/shop-demo` renders a complete worked month (all figures invented). The design decision: **a number carries its evidence in the type system**. `Shop\Truth\EvidenceType` {BANK_CONFIRMED, CARD_TERMINAL, PLATFORM_STATEMENT, CASH_COUNTED, SUPPLIER_INVOICE, FISCAL_REPORT, USER_DECLARED, RECURRING_SCHEDULE, ESTIMATED, AI_SUGGESTED} decides `Provenance` and `Certainty` and `isIndependentlyCorroborated()` (CASH_COUNTED is ACTUAL but not corroborated: the only witness is the person counting).

- **Truth** (`src/Truth/`): `Money` (integer grosze), `Provenance` {OFFICIAL_ACCOUNTING_FACT, ANALYTICAL_ESTIMATE, USER_DECLARATION, AI_SUGGESTION; `worst()`; `isBinding()` false for AI}, `Certainty` {ACTUAL, USER_DECLARED, EXPECTED, ESTIMATED; `worst()`; Polish labels RZECZYWISTE/ZADEKLAROWANE/OCZEKIWANE/SZACOWANE}, `Figure` (takes a `sourceReference`), `Total` (`of([])` → ESTIMATED/ANALYTICAL_ESTIMATE with zero and count 0, i.e. NO DATA; `describe()` renders the split), `ReviewFlag` (codes uppercase; severities INFO / REQUIRES_REVIEW / URGENT_REVIEW; refuses accusatory words; requires innocent explanations).
- **Page 1 Money** (`src/Money/`, `src/Platforms/`, `src/Cash/`): `AllocationSet`, `AllocationState` {UNALLOCATED, PARTIALLY_ALLOCATED, FULLY_ALLOCATED, OVER_ALLOCATED}, `MatchHistory`/`MatchRevision` (open → revision 1, correct → revision 2 with who/when/why; no delete), `PlatformSettlement` (`gross − commission − fees = expected` vs received; NO_PAYOUT_RECORDED never RECONCILED), `CashLedger` (`statement()` with running balance; a count must name its counter), `CashMovement`.
- **Page 2 Stock** (`src/Inventory/`): `Quantity` (units cannot be mixed), `Recipe`, `RecipeBook`, `TheoreticalConsumption` (no recipe → UNKNOWN, never zero), `StockLine`, `StockReconciliation` (`opening + purchases − theoretical = expected` vs counted; NOT_COUNTED never a match).
- **Page 3 Profit** (`src/Costs/`, `src/Profit/`, `src/Pricing/`): `CostCategory`, `CostEntryType`, `CostEntry` (document number), `RevenueChannel`, `ChannelResult` (`contribution()` — contribution is not profit), `ProfitStatement` (inherits worst certainty; never presented as tax profit), `ProductProfitability`, `PriceReview` (GREEN/AMBER/RED against a target margin; no method returns a new price).
- **Boundaries** (`src/Ai/`, `src/Comparison/`): `AiAction`, `AiBoundary` (`assertPermitted`, `permittedActions`, `forbiddenActions`), `AiBoundaryViolation`, `PendingSuggestion`, `AccountsSnapshot` (period, revenue, costs, importedBy, importedAt, sourceDescription — all required; provenance OFFICIAL_ACCOUNTING_FACT), `AccountsComparison` (reports, never writes).
- **Output** (`src/Monitoring/`, `src/Reporting/`): `Baseline` (`MINIMUM_PERIODS = 3`, median), `ShopMonitor`, `LossRanking` (notes never ranked as losses), `MonthlyManagementReport`, `ProfitStatementNote`, `TextReportRenderer`.

The three pages per `docs/BANKING_UX.md`: Money (ledger with running balances left, documents with allocation state right, platform payouts strip on top); Stock (one table with the formula as the header row, COMPLETE/PARTIAL check status); Profit (confirmed result and projected result side by side, cost groups, channels by contribution, products with the traffic-light review, "Where am I losing money?" ranked by money at stake). Status vocabulary: FULLY ALLOCATED, PARTIALLY ALLOCATED, UNRECONCILED, REQUIRES REVIEW, NOT COUNTED / NO DATA, plus one badge per amount: ACTUAL · EXPECTED · ESTIMATED · USER DECLARED. Thresholds in `shop-intelligence/.env.example` (SHOP_TARGET_MARGIN_PERCENT=60, SHOP_WARNING_MARGIN_PERCENT=50, SHOP_STOCK_TOLERANCE_PERCENT=2, SHOP_CASH_TOLERANCE_GROSZE=0, SHOP_REVENUE_DROP_ALERT_PERCENT=-15, SHOP_COST_RISE_ALERT_PERCENT=20) are invented defaults per the Fable briefing, not from the shop's data.
